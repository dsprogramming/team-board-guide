# Як вести борди для кількох команд: повний процес

> **Це загальна порада, а не документ конкретного проєкту.**
> Тут немає назв компаній, репозиторіїв, людей чи реальних задач: усі приклади вигадані й показують підхід.
> Зараз порада написана насамперед для Android-команди, яка переходить з Trello на GitHub, але процес однаковий для iOS, Android, вебу й бекенду.
> Коротка версія для Android-команди — у [README](README.md).

## Коротко

Задача на борді будь-якої команди рухається зліва направо через ті самі 6 статусів.
Done означає «перевірено на тестовому середовищі», а не «змерджено».
Цей документ описує, що означає кожна колонка, кожне поле і хто що робить.
Друга половина — вибір інструмента для кількох команд і QA: Jira, GitLab або GitHub.

**Для кого:**

- **Розробники** — як брати задачу, коли її рухати, що прив'язувати до PR.
- **Тімліди** — як планувати, що контролювати, які правила обов'язкові.
- **QA** — коли задача готова до тестування, куди заводити баги, як закривати.

## Цільова схема: команди і борди

Одна борда на команду з однаковими статусами й полями, плюс одне спільне подання для epics.
Між командами відрізняються лише назва п'ятого статусу (де саме тестується зміна) і значення поля Area.

| Команда | Борда | Репозиторій | Де перевіряється зміна |
|---|---|---|---|
| iOS | Окрема GitHub-борда | Репозиторій iOS | TestFlight |
| Android | Окрема GitHub-борда | Репозиторій Android | Google Play Internal testing |
| Веб + CMS | Окрема GitHub-борда | Репозиторій сайту | Staging |
| Бекенд | Окрема GitHub-борда | Репозиторій бекенду | Staging |
| Усі команди | Спільне подання Roadmap | — | — |

Типові проблеми, які варто шукати в себе:

- Одна з команд живе в окремому інструменті (наприклад, Trello) без зв'язку з PR.
- Бекенд не має своєї борди, і його баги лежать на борді іншої команди.
- Одна борда стала «спільною QA-бордою», куди звалюють баги всіх команд, тож PR іншої команди їх не закриває.

## Еталонна борда (GitHub Projects)

Борда — це GitHub Project рівня організації з поданням Board, колонки якого задає поле `Status`.

### 1. Доступ

1. Борда приватна: її бачать тільки члени організації з доступом до проєкту.
2. Усі issues з репозиторію команди потрапляють на борду автоматично.
3. Поля `Priority` і `Effort` — організаційні, тож їхні варіанти змінює лише адмін організації. Це свідомо: словник однаковий для всіх команд.

### 2. Колонки (статуси)

| # | Статус | Що означає | Умова входу | Хто рухає |
|---|---|---|---|---|
| 1 | **Backlog** | Зафіксовано, не заплановано | Автоматично при створенні issue | Автоматизація |
| 2 | **Ready** | Можна брати в роботу | Є критерії приймання і дизайн | Тімлід |
| 3 | **In Progress** | Хтось пише код | Є виконавець у `Assignees` | Розробник |
| 4 | **In Review** | PR відкрито, чекає рев'ю | PR прив'язаний до issue | Автоматизація або розробник |
| 5 | **На тесті** | Змерджено **і** є в білді для тестерів | PR змерджено, білд завантажено | Автоматизація + реліз-менеджер |
| 6 | **Done** | Перевірено на білді | QA підтвердив | QA |

- **П'ятого статусу бракує більшості борд.** Змерджений PR не можна протестувати, поки білд не завантажено.
- **Blocked — не статус.** Заблокована задача лишається у своїй реальній колонці, а причину пишуть у поле `Blocked by`.
- Кольори колонок ідуть по порядку, тому стан борди видно без читання підписів.

### 3. Поля задачі

| Поле | Значення | Обов'язкове | Правило |
|---|---|---|---|
| `Status` | 6 статусів вище | Так | Див. таблицю вище |
| `Team` | Backend · Web · iOS · Android | Так | Потрібне для Roadmap і фільтрів QA |
| `Priority` | Urgent · High · Medium · Low | Так, щоб вийти з Backlog | Організаційне, спільне для всіх борд |
| `Effort` | High · Medium · Low | Так, для Ready | Low — години, Medium — приблизно день, High — кілька днів (краще розбити) |
| `Work type` | Bug · Feature · Chore · Refactor · Spike | Так | Spike — дослідження з таймбоксом; результат — рішення, а не код |
| `Area` | Мобайл: Auth · Networking · Events · Profile · Notifications · Architecture · Build & Release · Design System; веб і бекенд — визначає тімлід | Так | Відповідає папкам фіч у застосунку |
| `Blocked by` | Посилання на задачу-блокер + короткий текст | Лише якщо блокер є | Наприклад, `waiting for backend endpoint` |
| `Build` | iOS — номер білда TestFlight; Android — versionCode; веб і бекенд — версія або тег на staging | На п'ятому статусі | Заповнює CI або реліз-менеджер |
| `QA result` | Passed · Failed · Not needed | Для Done | Done лише з Passed або Not needed |

Стандартні поля GitHub, які теж варто використовувати: `Assignees`, `Reviewers`, `Linked pull requests`, `Milestone`, `Parent issue` + `Sub-issues progress`, `Labels`.

### 4. Лейбли

Поля існують лише на борді, а лейбли працюють і в пошуку issues, і в PR, і в API, тому частину полів варто продублювати лейблами.

| Група | Лейбли |
|---|---|
| Пріоритет | `priority: urgent` · `priority: high` · `priority: medium` · `priority: low` |
| Область | `area: …` — той самий список, що й у полі `Area` |
| Джерело | `source: code-review` · `source: qa` … |

Список областей має бути один для лейблів і для поля.
Лейбл на кшталт `area: bug` дублює `Work type = Bug`, тому його не потрібно.

### 5. Автоматизації

| Автоматизація | Що робить |
|---|---|
| Auto-add to project | Кожна нова issue з репозиторію потрапляє на борду |
| Auto-add sub-issues to project | Підзадачі додаються разом із батьківською |
| Item added to project | Ставить `Status = Backlog` |
| Pull request linked to issue | Прив'язаний PR переводить задачу в In Review |
| Pull request merged | Мердж переводить задачу в п'ятий статус |
| Item closed | Закрита issue переходить у Done |
| Auto-close issue | Задача в Done закриває issue |

Перевірте в налаштуваннях борди, що `Pull request merged` ставить п'ятий статус, а не Done.

### 6. Стабільні ID у назвах

Якщо задачі з'явилися з аудиту чи рев'ю коду, дайте кожній стабільний префікс, наприклад `[S-2]` для безпеки чи `[B-6]` для бага.
Тоді той самий ID означає одне й те саме на борді, у коміті й у розмові: `Guard console logging behind DEBUG (S-2)`.

### 7. Правила борди

1. Одна задача — один результат. Якщо потрібно два PR, це дві задачі або батьківська з підзадачами.
2. Задача виходить з Backlog лише з написаними критеріями приймання.
3. Виправлення бага має регресійний тест, щойно в проєкті з'являться тести.
4. PR обов'язково прив'язаний до задачі (`Closes #N`), інакше автоматизації не спрацюють.

## Trello проти GitHub Projects

| Що | GitHub Projects | Trello |
|---|---|---|
| Статуси | 6: Backlog → Ready → In Progress → In Review → На тесті → Done | Зазвичай 4: To-do → Doing → On Review → Done |
| «Можна брати» | Ready | Немає, змішано в To-do |
| Тестування на білді | Окремий статус | Немає |
| Priority / Effort / Work type / Area | Окремі поля, спільні для всіх борд | Кольорові лейбли без назв |
| Blocked by | Поле | Немає |
| Зв'язок з PR | `Closes #N`, автоматичні переходи | Лише через Power-Up |
| Стабільний ID задачі | `#N` і префікс | Немає |
| Де живе | Поруч із кодом, той самий акаунт | Окремий сервіс і акаунт |

Trello зручний для однієї невеликої команди.
Але в ньому немає спільних з іншими бордами полів і зв'язку з PR, тому він заважає вести epics, які зачіпають кілька команд.
Типовий симптом: картка в Trello стоїть у Done, PR змерджено, а issue про той самий баг досі відкрита, і ще один дубль лежить на борді QA.

### Як перевести Trello-борду на спільний процес

1. Створити GitHub-борду копією еталонної: ті самі статуси, поля й автоматизації, а п'ятий статус для Android назвати Internal testing.
2. Разом із командою з'ясувати, що означають кольорові лейбли, і розкласти їх по Work type, Priority або Area.
3. Перенести картки в issues: To-do → Backlog (або Ready, якщо є критерії), Doing → In Progress, On Review → In Review, Done → Done або Internal testing, якщо зміну ще не перевірено на білді.
4. Карткам, які дублюють задачі інших платформ, дати спільний epic або хоча б посилання.
5. Після перенесення закрити Trello-борду для редагування, щоб не вести дві борди паралельно.

Питання до команди перед перенесенням:

- Що означає кожен колір лейбла?
- Хто на борді розробник, тімлід і QA?
- Що означає Done: «змерджено» чи «перевірено на білді»?
- Чи підключені Power-Ups, Custom Fields або правила автоматизації?

## Єдиний процес для бекенду, вебу і мобайлу

Якщо всі команди ведуть борди за одним набором статусів і полів, тімлід чи QA читає будь-яку борду без пояснень, а спільне подання Roadmap збирає задачі з усіх.

### 1. Статуси

Шість статусів однакові для всіх, відрізняється лише назва п'ятого.

| # | Статус | iOS | Android | Веб + CMS | Бекенд |
|---|---|---|---|---|---|
| 1 | Backlog | Backlog | Backlog | Backlog | Backlog |
| 2 | Ready | Ready | Ready | Ready | Ready |
| 3 | In Progress | In Progress | In Progress | In Progress | In Progress |
| 4 | In Review | In Review | In Review | In Review | In Review |
| 5 | На тесті | In TestFlight | Internal testing (Google Play) | In Staging | Deployed to staging |
| 6 | Done | Done | Done | Done | Done |

- **На тесті** означає одне й те саме для всіх: зміну змерджено й розгорнуто там, де QA може її перевірити, а номер білда чи версії записано в поле Build.
- **Done** — це «перевірено на тестовому середовищі», а не «у продакшені». Вихід у продакшен відстежує Milestone (версія застосунку або реліз вебу чи бекенду).
- На бекенді «на тесті» часто перевіряє не лише QA, а й клієнтська команда, яка чекала ендпойнт. Тоді її підтвердження вважається QA result = Passed.

### 2. Епіки, що зачіпають кілька команд

1. **Epic — окрема issue** з описом фічі для користувача й одним власником: тімлідом команди, у якої найбільше роботи.
2. **Підзадача в кожній команді**: sub-issue в репозиторії команди, яка сама потрапляє на її борду.
3. **Спершу контракт API**: перша підзадача бекенду — опис ендпойнтів, узгоджений з вебом і мобайлом. Клієнти пишуть код на моках, не чекаючи реалізації.
4. **Блокування — посиланням**: клієнтська підзадача, яка чекає ендпойнт, має в Blocked by посилання на бекенд-задачу. Блок знімається, коли та доходить до Deployed to staging.
5. **iOS і Android — парні підзадачі**: однакова назва й однакові критерії приймання, щоб QA перевіряв обидва застосунки одним сценарієм.
6. **Epic закривається**, коли всі підзадачі в Done. Користувачам фіча виходить, коли вона є в продакшені на всіх платформах або схована за флагом там, де ще не готова.
7. **Roadmap**: спільне подання лише з epics, з датами й прогресом підзадач. Тімліди раз на тиждень звіряють на ньому, хто кого блокує.

### 3. Приклад epic: скидання пароля з листа

Типова ситуація: посилання з листа для скидання пароля веде на `localhost` або не відкриває екран застосунку.
Баг помічають в Android, в iOS його ніхто не перевіряв, а причина — у бекенді, який формує посилання.

| Рівень | Репозиторій | Задача | Статус на старті | Blocked by |
|---|---|---|---|---|
| Epic | Репозиторій для epics | Скидання пароля за посиланням з листа працює на всіх платформах | Ready | — |
| Backend | Бекенд | Посилання в листі веде на робочу адресу для кожного середовища | Ready | — |
| Веб | Сайт | Сторінка або редирект `/reset-password`, якщо скидання йде через сайт | Backlog | Backend |
| Android | Android | Після переходу за посиланням можна задати новий пароль | Backlog | Backend |
| iOS | iOS | Перевірити той самий сценарій і виправити, якщо треба | Backlog | Backend |

1. Власник epic — тімлід бекенду, бо проблема починається з посилання, яке формує бекенд.
2. Разом із тімлідами клієнтів він вирішує, куди веде посилання: на сайт, у застосунок (deep link) чи туди й туди. Це «контракт» epic, і від нього залежить, чи потрібна веб-підзадача.
3. Бекенд-підзадача проходить Ready → In Progress → In Review → Deployed to staging, а номер версії пишуть у Build.
4. Щойно вона на staging, у клієнтських підзадач очищається Blocked by, і тімліди переносять їх у Ready.
5. Android та iOS мають однакові критерії приймання, і QA перевіряє обидва застосунки одним сценарієм: запит → лист → посилання → новий пароль → вхід.
6. Epic закривається, коли всі підзадачі в Done; на Roadmap він видно одним рядком із прогресом підзадач.

### 4. Definition of Done по командах

Спільне для всіх: PR змерджено з апрувом і зеленим CI, критерії приймання перевірено, QA result = Passed або Not needed.

| Команда | Де перевіряємо | Додатково до Done |
|---|---|---|
| iOS | Білд у TestFlight | Номер білда в Build |
| Android | Білд у Internal testing (Google Play) | versionCode у Build; релізний білд з R8 збирається без помилок |
| Веб + CMS | Staging | Версія або тег у Build; перевірено в підтримуваних браузерах |
| Бекенд | Staging | Міграції застосовано; документацію API оновлено; клієнтські команди повідомлено, якщо змінився контракт |

## Життєвий цикл задачі

Задача не перестрибує статуси: змерджена, але ще не на тестовому середовищі, вона ще не Done.
Заблокована задача стоїть на місці із заповненим `Blocked by`.

```
Backlog → Ready → In Progress → In Review → На тесті → Done
                       ↑                        │
                       └──── QA result: Failed ─┘
```

1. **Створення.** Будь-хто відкриває issue за шаблоном, і вона сама потрапляє в Backlog.
2. **Грумінг.** Тімлід дописує критерії приймання, ставить Priority, Effort, Work type, Area і переносить задачу в Ready.
3. **Робота.** Розробник призначає себе в `Assignees`, створює гілку й переносить задачу в In Progress.
4. **Рев'ю.** Відкритий PR із `Closes #N` переводить задачу в In Review; зауваження виправляють у тому самому PR.
5. **Білд.** Після мерджу та завантаження білда чи розгортання на staging задача переходить у п'ятий статус своєї команди, а номер пишуть у Build.
6. **Перевірка.** QA перевіряє критерії на цьому білді: Passed → Done, Failed → назад у In Progress.

## Що відбувається автоматично, а що руками

Руками людина робить лише три речі: пише issue, відкриває PR і ставить QA result.
Усе інше роблять автоматизації борди.

| # | Хто робить | Дія | Що GitHub робить сам | Статус після |
|---|---|---|---|---|
| 1 | Будь-хто | Створює issue в репозиторії команди | Auto-add to project додає її на борду; Item added to project ставить Status | Backlog |
| 2 | Будь-хто | Додає підзадачу (sub-issue) | Auto-add sub-issues додає її разом із батьківською | Backlog |
| 3 | Тімлід | Пише критерії приймання, ставить Priority, Effort, Work type, Area | — | Ready (вручну) |
| 4 | Розробник | Ставить себе в Assignees, створює гілку | — | In Progress (вручну) |
| 5 | Розробник | Відкриває PR з `Closes #N` | Pull request linked to issue рухає задачу | In Review |
| 6 | Рев'юер | Апрувить, PR мерджиться | Pull request merged рухає задачу | На тесті |
| 7 | Реліз-менеджер або CI | Завантажує білд, пише номер у Build | — | На тесті |
| 8 | QA | Перевіряє на білді, ставить QA result = Passed | — | Done (вручну) |
| 9 | — | — | Auto-close issue закриває issue | Done, issue закрита |

- Якщо issue закрили руками, Item closed сам переносить задачу в Done.
- Без `Closes #N` у PR кроки 5–6 не спрацюють, і задачу доведеться тягнути руками.
- Якщо задачі імпортують з документа (наприклад, з рев'ю коду), достатньо одного скрипта, що викликає `gh issue create` на кожен пункт. Далі нові задачі створюються як звичайні issues.

## Інструкція для QA: як заводити баги

Баг заводять як issue в репозиторії тієї команди, чий це код, за одним шаблоном для всіх команд.
На борду він потрапляє сам.

### 1. Куди заводити

| Де помітили баг | Репозиторій |
|---|---|
| Застосунок iOS | Репозиторій iOS |
| Застосунок Android | Репозиторій Android |
| Сайт або CMS | Репозиторій сайту |
| Помилка API: 500, неправильна відповідь, посилання з листа | Репозиторій бекенду |
| Незрозуміло, чия помилка | Репозиторій клієнта, де помітили; тімлід перенесе після розбору (Transfer issue) |

Префікси на кшталт `[AndroidTest]` чи `[Backend]` у назві не потрібні: команду видно з репозиторію та поля Team.

### 2. Крок за кроком

1. **Перевір дублі.** Пошукай за ключовим словом серед відкритих і закритих issues. Якщо такий баг уже є, додай коментар із номером свого білда, нового не створюй.
2. **New issue → шаблон Bug.** У назві — що зламано і де: «Вилітає після тапу на профіль», а не «Баг з профілем».
3. **Заповни шаблон:** білд і середовище, пристрій або браузер, кроки, очікуваний і фактичний результат, скріншот чи відео, серйозність.
4. **Прив'яжи до фічі.** Баг у задачі, яку ти зараз перевіряєш, оформлюєш як sub-issue цієї задачі; у фічі з epic ставиш посилання на epic.
5. **Натисни Create.** Далі все відбувається само: баг потрапляє на борду команди в Backlog з Work type = Bug.
6. **Тімлід розбирає баг протягом 1 робочого дня:** ставить Priority, Area і переносить у Ready або закриває як дубль чи «не баг» із коментарем.
7. **Після виправлення** баг повертається до тебе в п'ятому статусі з номером у Build. Перевір на цьому білді: Passed → Done, Failed → назад у In Progress із коментарем.

### 3. Серйозність і пріоритет

Серйозність (наскільки все погано) ставить QA, а Priority (коли це робити) — тімлід.

| Серйозність | Коли | Приклад | Типовий Priority |
|---|---|---|---|
| Blocker | Креш, втрата даних, не вдається увійти чи заплатити | Застосунок вилітає після тапу на профіль | Urgent |
| Major | Функція не працює, але є обхідний шлях | Не можна змінити дату народження | High |
| Minor | Валідація, верстка, текст | У полі телефону немає плейсхолдера | Medium / Low |

### 4. Чого не робити

- Не ставити Bug як статус: Bug — це Work type, а задача стоїть у своєму реальному статусі.
- Не створювати draft-картки прямо на борді: їх не видно в репозиторії, і PR їх не закриє.
- Не заводити баг однієї команди в репозиторії іншої, бо тоді PR його не закриє.
- Не переводити задачу в Done без перевірки на білді та без QA result.

### 5. Якщо перевірка не пройшла

1. QA ставить `QA result = Failed` і пише коментар із номером білда.
2. Якщо не виконано критерії приймання самої задачі, вона повертається в **In Progress** до того самого розробника.
3. Якщо знайдено іншу проблему, QA заводить новий Bug як підзадачу фічі, а сама фіча може йти в Done.

### 6. Що додати до борди для QA

- **Поле `Build`** — номер білда або версія на staging; заповнює CI (для мобайлу — fastlane) або реліз-менеджер.
- **Поле `QA result`** — Passed · Failed · Not needed.
- **Розділ «How to test» у шаблоні PR** — екран, кроки, тестовий акаунт, середовище.
- **Подання «QA»** — п'ятий статус усіх команд, групування за Team і Build. QA бачить лише те, що чекає перевірки, білд за білдом.

## Три варіанти: Jira, GitLab або GitHub

Різниця між варіантами не в колонках, адже їх можна зробити однаковими скрізь.
Вона в тому, скільки інструментів треба синхронізувати і де живе QA.

- **А. Усі в Jira** — задачі, спринти й тести в Jira, а код лишається в GitHub чи GitLab і під'єднується інтеграцією.
- **Б. Усі в GitLab** — код, CI, задачі й борди в одному місці, але репозиторії доведеться переносити з GitHub.
- **В. Усі в GitHub** — GitHub Projects + Actions, а тест-кейси в окремому інструменті.

Trello як інструмент для кількох команд не розглядаємо.
Без Power-Up у ньому немає зв'язку задачі з PR, немає спільних полів і правил переходу між бордами, а epics між командами довелося б синхронізувати вручну.

| Критерій | А. Jira | Б. GitLab | В. GitHub |
|---|---|---|---|
| Статуси і переходи | Workflow з правилами: хто може перевести, обов'язкові поля на переході | Scoped-лейбли `workflow::*` або поле Status; правил переходу майже немає | Поле Status; будь-хто перетягує будь-куди |
| Зв'язок з кодом | Через інтеграцію, ключ `KEY-123` у гілці й коміті | Нативний: MR закриває issue | Нативний: PR закриває issue |
| Спринти і планування | Найсильніше: Scrum/Kanban, velocity, burndown, roadmap між командами | Iterations, milestones, epics (платні тарифи) | Iteration-поле, Roadmap-подання, без burndown |
| Кілька команд | Окремі проєкти + спільна планувальна борда | Групові борди на рівні групи | Організаційні поля + окремі борди |
| QA і тест-кейси | Плагіни Xray / Zephyr: кейси, прогони, зв'язок баг ↔ кейс | Test cases — лише в найдорожчому тарифі | Немає; потрібен окремий інструмент (TestRail, Qase) |
| Звіти для менеджменту | Дашборди, JQL, готові звіти | Базова аналітика, value stream у платних тарифах | Insights-графіки борди, скромно |
| CI/CD для мобайлу | Не стосується | GitLab CI; для iOS потрібні macOS-раннери | GitHub Actions з macOS-раннерами |
| Вартість переходу | Середня: перенести задачі, налаштувати workflow та інтеграцію | Висока: репозиторії, fastlane, секрети, автоматизації, звички команди | Низька, якщо код уже в GitHub |
| Адміністрування | Потрібна людина, що відповідає за Jira | Один інструмент — менше адмінки | Мінімальне |
| Доступ для нетехнічних людей | Найзручніше | Потрібен акаунт і звикання до інтерфейсу | Те саме, що в GitLab |

**Коли обирати кожен:**

- **Jira** — коли команд понад дві-три, є PM і замовники, а QA потрібен повноцінний тест-менеджмент.
- **GitLab** — коли компанія вже на GitLab або потрібен self-hosted; переїжджати лише заради борди не варто.
- **GitHub** — коли команда технічна, до ~15 людей, і QA готовий вести кейси в окремому сервісі.

Ціни й ліміти тарифів звіряйте на сайтах вендорів перед рішенням.

### Як це виглядає для QA

| Що потрібно QA | А. Jira | Б. GitLab | В. GitHub |
|---|---|---|---|
| Статус «чекає тесту» | Статус `In QA`, перехід у Done лише для групи QA | Лейбл `workflow::testing` | П'ятий статус борди |
| Заборона Done без перевірки | Так, через умови переходу | Ні, лише домовленість | Ні, лише домовленість |
| Тест-кейси й регресійні прогони | Xray / Zephyr прямо в задачах | Test cases (топовий тариф) або зовнішній сервіс | Зовнішній сервіс із посиланнями на issue |
| Зв'язок баг ↔ фіча | Issue links (`is caused by`, `blocks`) | Linked items, підзадачі | Sub-issues |
| Звіт перед релізом | Дашборд «баги по релізу» через JQL | Фільтр по milestone | Подання з фільтром по milestone |

Для QA найзручніша Jira + Xray: кейси, прогони й баги в одному місці, і система сама не пускає задачу в Done без перевірки.
Для невеликої QA-команди (1–2 людини) GitHub + Qase дає той самий результат без переїзду.

## Процеси для великої команди

Ці правила однакові для будь-якого інструмента; інструмент лише визначає, скільки з них перевіряє машина, а скільки людина.

### 1. Ролі

| Роль | Відповідає за | Рухає задачу |
|---|---|---|
| Тімлід | Порядок Backlog, пріоритети, критерії приймання, WIP-ліміти | Backlog → Ready |
| Розробник | Код, PR, прив'язка PR до задачі, нотатки для QA | Ready → In Progress → In Review |
| Рев'юер | Рев'ю протягом 1 робочого дня | Апрув → мердж |
| Реліз-менеджер (черговий) | Білд для тестерів, номер білда в задачах | → На тесті |
| QA | Перевірка на білді, баг-репорти, регрес перед релізом | На тесті → Done або назад |

### 2. Ритуали

| Зустріч | Як часто | Хто | Що робимо з бордою |
|---|---|---|---|
| Стендап | Щодня, 15 хв | Команда | Ідемо по борді **справа наліво**: спочатку те, що ближче до Done |
| Грумінг | Раз на тиждень | Тімлід + 1–2 розробники + QA | Критерії приймання, Effort, перенесення в Ready |
| Планування | На початку ітерації (2 тижні) | Команда | Вибір задач з Ready в ітерацію |
| Ретро | Наприкінці ітерації | Команда | Де задачі застрягли і чому |
| Синк тімлідів | Раз на тиждень | Тімліди всіх команд | Міжкомандні блокери (`Blocked by`) |

### 3. WIP-ліміти

- **In Progress:** не більше 1 задачі на розробника (2 — якщо одна заблокована).
- **In Review:** не більше задач, ніж розробників. Якщо ліміт перевищено, спершу рев'ю, а потім новий код.
- **Ready:** запас на 1–2 тижні, не більше; усе інше чекає в Backlog.

### 4. Definition of Ready і Definition of Done

**Ready**, коли:

- Написано критерії приймання
- Є дизайн або явно сказано, що він не потрібен
- Заповнено `Priority`, `Effort`, `Work type`, `Area`
- Effort не High (інакше задачу треба розбити на підзадачі)
- Немає відкритого блокера від бекенду

**Done**, коли:

- PR змерджено з апрувом і зеленим CI
- Зміна є на тестовому середовищі команди, номер білда чи версії вказано в Build
- QA перевірив критерії приймання на цьому білді
- Для Bug є регресійний тест

### 5. Іменування

| Що | Формат | Приклад |
|---|---|---|
| Гілка | `<тип>/<id>-<коротко>` | `fix/42-profile-crash` |
| Коміт | Дієслово в наказовому способі + ID у дужках | `Guard console logging behind DEBUG (S-2)` |
| PR | Як коміт + `Closes #N` в описі | `Closes #42` |

У Jira замість `#N` використовують ключ `KEY-123` у назві гілки, бо без нього інтеграція не зв'яже PR із задачею.

### 6. Коли команд кілька

- Одна борда на команду з **однаковими** статусами й полями.
- Фіча, що зачіпає кілька команд, оформлюється як батьківська задача (epic) з підзадачею на кожній борді.
- Для менеджменту є окреме подання Roadmap: лише epics, по датах.
- Заблокована міжкомандна задача має в `Blocked by` посилання на задачу, що її блокує, а не лише текст.

## Шаблон баг-репорту

```
**Білд:** 1.4.0 (212) · **Середовище:** Dev / Prod
**Пристрій:** Pixel 7, Android 14
**Кроки:**
1. …
**Очікувано:** …
**Фактично:** …
**Скріншот / відео:** …
**Серйозність:** Blocker / Major / Minor
```

У GitHub це issue form у `.github/ISSUE_TEMPLATE/bug.yml` (готові шаблони — у [README](README.md#шаблони-в-репозиторії)), у GitLab — `.gitlab/issue_templates/Bug.md`, у Jira — поля типу Bug.

## Рекомендація

**Якщо код уже в GitHub, ведіть усі команди в GitHub Projects за єдиним процесом, а до Jira переходьте, коли спрацює один із тригерів нижче.**
Еталонну борду можна копіювати для кожної команди.
Trello для однієї з команд залишати не варто: у ньому немає статусу тестування, спільних полів і зв'язку з PR, тож спільні epics довелося б вести вручну.
Найслабше місце GitHub — тест-кейси та звіти; їх закривають окремим інструментом для кейсів, полем Team і поданнями Roadmap та QA.
GitLab варто розглядати, лише якщо компанія переносить туди весь код, а не заради борди.

**Тригери переходу на Jira:**

- Спільні релізи кількох команд перестають вміщатися в Roadmap-подання: потрібні залежності між epics, дати та звіт про ризики.
- PM чи замовнику потрібні регулярні звіти, яких GitHub не дає.
- QA веде понад ~200 тест-кейсів і регулярні регресійні прогони.
- Попри домовленості, повторюється робота в обхід статусів (Done без QA).

### План на перші 2 тижні

- [ ] Узгодити лейбли `area:` з полем `Area`
- [ ] Перевірити цільові статуси автоматизацій `Pull request linked` і `Pull request merged`
- [ ] Додати поля `Team`, `Build` і `QA result`
- [ ] Створити подання «QA», «Мої задачі», «Roadmap»
- [ ] Додати шаблони Bug, Feature і PR у кожен репозиторій
- [ ] Передати заповнення `Build` у CI (fastlane) після завантаження білда
- [ ] Разом із QA обрати інструмент для тест-кейсів
- [ ] Перенести команду, яка живе в Trello, на GitHub-борду
- [ ] Створити борду для бекенду, якщо її немає
- [ ] Перенести баги кожної команди в її репозиторій і закрити дублі

### Питання, які треба закрити

- Скільки команд і людей працюватиме на бордах через 6 місяців?
- Чи є в компанії вже оплачена Jira або GitLab?
- Скільки людей у QA і чи потрібен їм повний тест-менеджмент уже зараз?
- Де живуть epics: в окремому репозиторії для планування чи в репозиторії команди-власника?
